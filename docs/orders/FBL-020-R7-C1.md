## Required outcomes

### 1. Clean mutation provenance

Move temporary PID/state outside the repository or clean it reliably.

CI must hard-fail unless the runtime mutation artifact reports all of:

* baseline green;
* zero survivors;
* final commit correctly identified;
* `tree_dirty: false`.

Do not merely edit the artifact.

### 2. Real runtime/migration credential separation

API and worker must authenticate using a distinct, non-owner, non-superuser runtime
database login. Merely connecting as the owner and issuing `SET ROLE`, including through
startup options, is insufficient.

Prove that the actual runtime connection:

* cannot regain migration-owner authority with `RESET ROLE`;
* cannot assume the evidence-owner or migration-owner role;
* cannot disable triggers, perform unauthorized DDL, or modify the migration ledger;
* cannot directly insert normalized child evidence, even with a forged GUC;
* can insert an authorized parent decision and cause database-owned normalization.

Compose and production startup must fail closed when the application is configured with
an owner/superuser credential or the required runtime posture is absent. Do not
hard-code or disclose credentials.

### 3. Structural authority classification

Action names may remain naming conventions, but no prefix may determine authority.

Use explicit structural action classification or an equivalent design so that:

* customer-tenant and customer-resource actions always require tenant authorization and,
  for platform support, valid delegation;
* genuine control-plane actions are platform-scoped, have no authorization tenant, and
  carry no customer-resource payload;
* catalog construction rejects contradictory definitions;
* renaming an action cannot change its authority plane.

Prove that a `platform.*`-named customer-resource action cannot bypass delegation and
that a genuine control-plane action still succeeds.

### 4. Support authority must remain live at evidence-write time

A support ALLOW must be rejected if the supporting platform role binding is revoked,
disabled, or outside its effective window when evidence is actually inserted—even if it
was valid when policy evaluation began.

Prove the evaluation-to-write race directly, with no policy or audit ALLOW left behind
after refusal. Include an active-binding control.

### 5. Approved support scope must cover the actual resource

At evidence-write time, relate the approved support scope to the database-resolved
resource ancestry.

Prove:

* rooftop-A approval plus rooftop-B resource refuses;
* same-rooftop access succeeds;
* a valid ancestor scope may reach a descendant;
* nonexistent and foreign resources refuse.

Do not rely solely on the runtime resolver; ordinary runtime credentials must be unable
to forge the evidence directly.

### 6. Close the `system` evidence bypass

`actor_type='system'` must not be a caller-selectable escape from actor, credential,
tenant, or resource validation.

Either prohibit system resource ALLOWs or require every such ALLOW to name a tenant and
use database-resolved resource ancestry. A system row must not carry human actor,
credential, support-session, or delegated-support evidence.

Prove fabricated snapshots, nonexistent resources, foreign resources, and mixed
human/system evidence all refuse. If a legitimate system lane remains, include one
structural positive control.

### 7. Validate the complete approval transition

Validate the complete approval invariant whenever a request enters or remains in
`approved`, not only when its grant ID changes.

Prevent staged pending/denied-to-approved transitions from bypassing grant, scope,
ancestor, decider, or timing validation. Constrain terminal transitions truthfully.

Prove staged approval refuses for nonexistent, foreign, inactive, future, expired, and
inactive-ancestor scopes. Include a valid atomic approval control.

### 8. Enforce retained-state upgrade requirements

The populated upgrade must inspect all retained request/session actor and tenant tuple
mismatches required by R7, not only currently live delegations. It must also identify
invalid standing approved scopes.

Irreparable conflicts must:

* refuse before partially landing the correction;
* report an exact count and bounded actionable identifiers;
* leave historical evidence untouched;
* never invent an approval or silently validate an incoherent constraint.

A clean upgrade must finish with the intended constraints validated and converge with a
fresh database.
