# FBL-020-R7-A1 — order text, checked in verbatim

Transcribed from the architect's message of 2026-08-21, sent immediately after
FBL-020-R7 (docs/orders/FBL-020-R7.md). The architect's covering words: "The
earlier R7 order over-constrained Fable. The one-commit rule, mandatory draft PR,
stop-on-first-red rule, prescribed database design, exact test names, and
prohibition on corrective pushes could slow implementation and create the same
loop we want to eliminate. Keep only the required security outcomes, forward-only
migration law, truthful evidence, and green acceptance gates. Send R7 first, then
send this amendment immediately afterward. This amendment controls wherever the
two conflict."

FBL-020-R7-A1 — Implementation Freedom Amendment

This amendment is part of FBL-020-R7 and supersedes any conflicting
implementation-method, Git-workflow, commit-count, file-scope, test-naming, or
packaging restriction in the original R7 order.

The required security outcomes remain unchanged. Fable is authorized to choose
the most effective engineering method for achieving them.

1. General implementation authority

Fable may:

* Modify any repository file reasonably necessary to satisfy FBL-020-R7.
* Add, remove, rename, or reorganize source files, tests, scripts, migrations,
  configuration, CI steps, documentation, roles, fixtures, and supporting
  utilities.
* Refactor adjacent code when necessary to implement a correct, maintainable
  solution.
* Add dependencies when justified, locked, security-reviewed, and compatible
  with the existing architecture.
* Use Docker, PostgreSQL, GitHub Actions, local databases, temporary
  environments, network access, command-line tools, and automation as needed.
* Run parallel investigations, tests, audits, or review processes when they help
  resolve a concrete implementation question.
* Correct additional defects discovered while working when they are directly
  related to identity, authorization, evidence integrity, migration safety, CI
  reliability, or the R7 acceptance requirements.
* Record a concise ADR when the best solution materially changes an existing
  architectural decision.

There is no artificial file allowlist.

2. Technical-design freedom

The designs stated in R7—composite foreign keys, database roles,
`SECURITY DEFINER` functions, resource-scope registries, database authority
functions, evidence-version changes, or similar mechanisms—are approved
reference designs, not mandatory implementations.

Fable may use a different design if it:

1. Makes the prohibited state unrepresentable or reliably refused by PostgreSQL.
2. Preserves tenant isolation and append-only evidence.
3. Cannot be bypassed by ordinary application/runtime credentials.
4. Works on both a fresh database and an upgraded populated database.
5. Is exercised through real production paths and direct-SQL adversarial tests.
6. Produces independently reviewable evidence.
7. Does not weaken an existing accepted control.

The implementation may consolidate several findings under one stronger
structural solution. It does not need to reproduce the architect's proposed
internal mechanics clause by clause when a simpler or stronger design closes the
same outcomes.

3. Migration authority

The forward-only migration rule remains mandatory:

* Migrations `000` and `049`–`058` are immutable.
* Schema corrections must begin with migration `059`.
* Additional forward migrations after `059` are allowed if genuinely needed.
* Historical policy decisions may not be rewritten, deleted, or supplied with
  invented approvals.
* Irreparable retained-state conflicts must be reported truthfully with
  actionable identifiers.
* Fresh and populated upgrade paths must converge to the same schema.

Fable may determine the final structure, evidence version, reconciliation
strategy, privilege model, and database functions necessary to meet these rules.

4. Git and GitHub authority

Fable is authorized to use the repository normally.

Fable may:

* Create and use branches.
* Commit as often as useful.
* Push intermediate and final commits.
* Open, update, close, or replace pull requests.
* Rerun GitHub Actions.
* Make corrective commits after failed CI runs.
* Rebase or squash when useful.
* Use `--force-with-lease` on a Fable-owned working branch when necessary.
* Fast-forward or merge to `main` after the intended final tree is green,
  provided repository protections permit it.
* Use an already-authorized Personal Access Token or other configured GitHub
  credential for cloning, fetching, pushing, API access, PR operations, workflow
  inspection, and artifact download.

The previous one-code-commit limit is removed for R7. A reasonable number of
honest, forward-moving commits is acceptable. Failed runs and corrective commits
must be disclosed, but they are not themselves grounds for rejection.

Credentials must never be printed, logged, embedded in a remote URL that remains
stored, committed, included in an artifact, or copied into documentation. Any
temporary credential-bearing remote configuration must be scrubbed after use.

5. CI and iteration authority

Fable does not have to stop after the first red run.

When CI or a local gate fails, Fable may diagnose, correct, commit, push, and
rerun until the intended final tree is green.

Iteration is considered forward-moving when each cycle:

* identifies a specific failure or missing invariant;
* changes implementation, tests, configuration, or evidence to address it; and
* re-verifies the affected surface.

Fable should stop and report only when:

* owner-controlled credentials, permissions, infrastructure, or external records
  are required;
* a destructive or irreversible choice requires owner authorization;
* requirements conflict in a way that materially changes product behavior;
* the same blocker persists after reasonable technically distinct attempts with
  no new diagnosis; or
* all R7 outcomes are green and the return package is ready.

Routine CI failures, test defects, formatting failures, packaging problems, or
ordinary implementation decisions are not stop conditions.

6. Testing and mutation flexibility

The behaviors and adversarial cases required by R7 remain mandatory, but exact
test names, test-file placement, mutation identifiers, and internal fixture
structure are flexible.

Equivalent proof is acceptable when the requirement map clearly identifies:

* the requirement;
* the production control;
* the positive control;
* the negative or adversarial case;
* the mutation or revert proof; and
* the resulting evidence.

Fable may combine tests when one genuine end-to-end case independently proves
several related requirements. However, the proof must remain non-vacuous and
must identify which predicate failed.

Mutation testing must finish with:

* every baseline green;
* zero surviving required mutations; and
* no result generated from a poisoned or already-failing baseline.

The existing test and suite level may not regress, and no failed, cancelled,
skipped, or todo result may be hidden or waived.

Quality baselines may be reduced but may not be raised merely to admit new
findings.

7. Documentation and closeout flexibility

Fable may update documentation whenever necessary and may use a
documentation-only closeout commit if that is the cleanest truthful method.

Avoid manually duplicating moving facts such as SHAs, run IDs, counts, and
commit distances. Prefer one canonical machine-readable record with other
documents referring to it.

Additional documentation review is allowed when it investigates a concrete
contradiction or acceptance requirement. Repeated general narrative sweeps are
unnecessary after deterministic gates and the authoritative record agree.

The checked-in repository does not need to contain a run ID that could not exist
when its commit was created. The external return package may provide the final
commit-to-run binding.

8. Evidence-package flexibility

The exact folder names and manifest format proposed in R7 are recommendations.

Any final package structure is acceptable if an independent reviewer can verify:

* repository identity;
* final commit and tree;
* exact source bytes;
* exact-SHA workflow run;
* every required job conclusion;
* CI artifacts and their hashes;
* test and mutation results;
* migration-chain integrity;
* package checksum; and
* remaining external blockers.

The source archive must come from the final Git object or otherwise reproduce
every Git blob and mode exactly. A working-tree ZIP that silently converts LF to
CRLF is not sufficient.

Fable may generate the final package outside the repository after CI succeeds
and may upload or transfer it using the available authorized mechanism.

9. Non-negotiable outcomes

Implementation freedom does not relax these outcomes:

* Actual database completion/write time must govern expiry and authority
  liveness.
* Missing callback purpose must fail closed.
* Reauthentication terminal reasons must be truthful.
* Support requests, approvals, sessions, actors, tenants, actions, scopes,
  durations, and evidence must be relationally coherent.
* Action-name prefixes alone cannot bypass tenant delegation.
* Resource authorization evidence must be bound to the resource's real tenant
  and organization ancestry.
* Tenant, organization, binding, and support authority must be active and
  effective when used.
* An ordinary runtime database credential cannot forge normalized evidence or
  directly exercise migration-owner authority.
* Historical evidence may not be rewritten or supplemented with invented facts.
* Prior migrations remain immutable.
* All required tests, mutations, upgrade drills, architecture checks, security
  scans, dependency checks, container checks, and exact-SHA CI jobs must be
  green.
* Evidence and documentation must be truthful.
* The two supplied project copies remain Version 1.0 until the owner/reviewer
  replaces them.
* Live WorkOS certification remains external and undischarged.
* FBL-030 remains blocked until architect acceptance of FBL-020.

10. Completion authority

Fable may continue autonomously through implementation, correction, CI,
packaging, and delivery.

When the required outcomes are green:

1. Reconcile the final documentation once.
2. Produce the independently verifiable final package.
3. Report the final commit, tree, CI run, artifacts, package checksum, and
   remaining external blockers.
4. Stop for architect acceptance.

Do not begin FBL-030 merely because Fable's implementation and CI are green.
Architect acceptance remains the release gate.
